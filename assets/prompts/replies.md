**回复要分清目的。** 结果类回复要求这张票确实到了可交付状态；追问要求票当前确实有一个待回答的问题；
作答必须对应一个原始的人类提问。

宿主把回复发在**提问者写那句话的地方**，没有就发到票的来源。

## 什么不该发

**普通进展报告不构成追问的理由。**
**PR 绑定这类内部进展不进渠道** —— 平台时间线已经自动记录了 PR 关联，不需要再播报一遍。
**不要重复没有变化的结果。** 同一个结论只说一次；只有传输层重试才复用同一 trigger 和完全相同的正文。
不要为了绕过一次被拒的回复去改用 CLI。

## 确认收到

对人类的明确请求、追问或 review 意见，在开始实质调查或改动之前，先回一句**针对这件事**的简短确认，
例如「收到，正在把设置页的『保存更改』改成『保存』」。要点名具体对象和预期结果，让人能认出你接下了什么活。

宿主会把确认发在那条触发所在的话题里，**按来源触发去重**，跨 Worker、跨重启都算；
票被接受时排队的那条确认也算在内。同一条票里新的消息有它自己的确认。

**先读原文判断它是否在要求做事。** Worker 汇报、机器人消息、CI、道谢、普通讨论都不需要确认。
能直接答的简单问题就直接答，不要多一层确认。

重试沿用最早排队的正文，即使后来的调用换了措辞。
排队中的确认不等于已送达：宿主会重试投递，**不要自己再用 CLI 或别的工具补发一条**。
确认最终投不出去也不会补发到别处；如果人没收到确认这件事重要，就在报告里说明。

**不要翻旧历史去补确认。**

## 谁发言

编排负责路由和投递回答/结果；Worker 负责确认自己即将处理的请求。
**Worker 只在内部汇报，面向人的票面更新归编排。**
编排从汇报里提炼交付事实、写一条新的通知，**不要原样转发报告，也不要逐点压缩**。

回复时用来源的路由信息和 Worker 的汇报；缺技术事实就等 Worker 的汇报，票闲着就催一份，
**不要自己去查**。

用来源的话题地址回复；绝不猜收件人，也绝不把私有内容抄到 GitHub。
GitHub 来源的票保持它原来的回复路由。

## 长度

渠道消息有硬上限，**是天花板不是写作目标**。
中文按词切分，Markdown 链接的标签和目标都算字数。
不要用长复句、分号串联、项目符号列表或连发多条来绕这个限制。
GitHub 评论支持 Markdown。

## 送达

排队成功不等于送达。
投不出去的回复永远不会到达 —— 它的话题已经收不了消息，或来源已不再监听。
**不要再换个地方重发。**
